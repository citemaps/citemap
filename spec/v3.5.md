# citemap.json Specification v3.5

> The catch-up release: everything producers have published since v3.4, written down. Graph vocabulary for products, brands and media; Media formats; catalog lifecycle; location geo and hours; third-party corroboration; business relationships; content files for large records; a computable citemap level. Strictly additive on v3.4.

**Status:** Release candidate
**Version:** 3.5
**Date:** 2026-11-23
**Authors:** Brian Pofahl
**License:** CC BY 4.0
**Schema:** https://citemaps.org/schema/v3.5/citemap.schema.json
**Vocabulary registry:** [./registry/v3.5-vocabulary.md](./registry/v3.5-vocabulary.md)
**Backward Compatibility:** Every valid v2.0, v3.0, v3.1, v3.2, v3.3 and v3.4 citemap validates against v3.5 with at most a `version` field bump.

---

## Overview

v3.4 (2026-06-02) was a vocabulary bump. Between v3.4 and v3.5 the reference producer (EntityGraph Studio) kept shipping: product and brand graph nodes, a Media model with podcasts and talks, third-party corroboration, client and partner relationships, location coordinates and hours, discontinued offerings, and content files for records too large for one file. Those fields have been in published citemaps without spec text, some since June and some for only days. v3.5 writes them down.

The method behind it: new structure is proven on real entities in a producer first, then published to the spec as a collection. Nothing in v3.5 is speculative. Every field, node type and edge type described here is emitted in the wild today; the release gives each one a definition, a validator rule and a registry entry. Proposals that are not yet emitted anywhere are listed in [§15](#15-not-in-v35) and wait for a later version.

The release covers eight areas:

1. **Graph vocabulary (§3).** Sixteen edge types graduate into the registry (`brand`, `manufacturer`, `makesOffer`, `creator`, `about`, `authored`, `featuredIn`, `mentionedIn`, `publishedOn`, `channelOf`, `producedAt`, `featuring`, `recordedIn`, `client`, `agency`, `partner`). Until now they shipped under the extension URL `https://citemaps.org/ext/v1/types/{name}`; both forms stay valid permanently. New node types (Brand, Product, ProductGroup, MediaChannel, media nodes), a recommended `@id` scheme, and a reachability rule that matches how real graphs are built.
2. **Brand and identity fields (§4).** `shortName`, `alternateName`, `numberOfEmployees`, `mission`, `languagesSupported`, `guarantees`, `accessibility`, `diversityOwnership`, brand-level `areaServed`, list-shaped `notableFor`, `disambiguatingDescription`, `distinctFrom[]`, and the `@type` mapping for the brand object.
3. **Catalog and locations (§5).** Product variants, product `@id` rules, the reseller pattern, dated discontinuation (`lifecycle`), location coordinates, time zone, ISO country codes, `openingHours`, and which brands are made at which location.
4. **Media (§6).** Channels, videos, podcasts, talks and social posts, with one shared set of fields and a connection model for who and what each item is about.
5. **Evidence (§7).** `corroboratedBy[]` (third-party pages that mention the entity, reviewed by a person at the entity), the schema.org `subjectOf` mirror on the brand and on individual nodes, memberships with context, and `businessRelationships[]` (clients, agencies, partners) backed by public pages.
6. **Content files (§8).** A main file that stays under the size AI fetch tools read, with Media and products in typed content files it lists. The sitemap-index pattern applied to a citemap.
7. **Citemap level (§9).** A level formula that can be computed from the file alone and no longer depends on the retired v3.0 module catalog.
8. **Registry conventions (§10).** DNS-verified ownership and publisher-submitted ("pushed") citemaps.

Sections [§2](#2-foundational-sections-updated-definitions) and [§1](#1-document-shape) also give first full definitions to keys that every citemap has carried since v3.0 but that no spec version described completely (`citationContract` keys, the `citemap` block, `trust.perField` tiers, `temporalRecord` rows).

### Design principle: describe what is published

v3.5 adds no field that is not already emitted. Where the reference producer and an earlier spec sketch disagreed, and no other producer implemented the sketch, v3.5 adopts the published form (for example the `trust.perField` tiers in §2.2). Where the producer breaks a rule an earlier spec states, the rule stands and the producer is fixed (for example former team members in `employee`, §4.6).

### Design principle: additive, never breaking

Every v3.4 document is a valid v3.5 document after a `version` bump. Nothing is removed. Deprecated forms (§12) produce warnings, never errors, and stay readable. Removal of anything deprecated here waits for a major version.

### Conventions

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119). `{origin}` means the scheme and host of `brand.url` (for `https://example.com/about`, `https://example.com`). Field tables list the type, whether the field is required, and the meaning. A field not marked required is optional. Producers MUST omit optional fields rather than emit `null`, empty strings or empty arrays, except for the always-on sections in §2, which emit their empty form.

## 1. Document shape

### 1.1 Top-level keys

A v3.5 main file carries these top-level keys. Order is not significant to JSON parsers, but AI fetch tools often read only the start of a file, so producers SHOULD emit keys in the order shown: identity and the content-file index first, bulk last.

| Key | Type | Required | Meaning |
|---|---|---|---|
| `@context` | string | Yes | `"https://citemaps.org/v3.5"`. |
| `@type` | string | Yes | `"Citemap"`. |
| `version` | string | Yes | `"3.5"`. |
| `citemapVersion` | string | No | Same value as `version`. An alias kept for readers written against v3.0 (§12). |
| `$schema` | string | No | `"https://citemaps.org/schema/v3.5/citemap.schema.json"`. |
| `generatedBy` | string | No | Name of the producing tool. |
| `citationContract` | object | Yes | How to cite the entity (§1.2). |
| `brand` | object | Yes | The entity (v3.0, v3.3 §4, §4 below). |
| `contentFiles` | array | No | Index of content files (§8). When present, it SHOULD come right after `brand`. |
| `lastVerified` | date | Yes | Date the producer last generated or confirmed the record (`YYYY-MM-DD`). |
| `answerContent` | array | Yes | Authored Q&A (§2.5). `[]` when empty. |
| `trust` | object | Yes | Per-field trust tiers (§2.2). |
| `temporalRecord` | array | Yes | Dated events (§2.3). `[]` when empty. |
| `policy` | object | Yes | Publisher policies (§2.4). `{}` when empty. |
| `verification` | object | Yes | Third-party-issued claims (§2.6). `{ "claims": [] }` when empty. |
| `@graph` | array | No | Related entities (v3.3 §1.3, §3 below). |
| `relationships` | array | No | Edges between entities (v3.3 §1.4, §3 below). |
| vertical module keys | object | No | Per-vertical data (§2.8). |
| `verifiedClaims` | array | No | Registered identifiers (v3.0 §5, §2.7 below). |
| `citemapLevel` | integer | No | Level the producer claims (§9). |
| `citemap` | object | No | Authorship of the file itself (§1.3). |

`contact` (v2.0) remains valid and is no longer emitted by the reference producer; entity contact data lives in `brand` (`email`, `brand.locations[].phone`).

### 1.2 `citationContract`

v3.0 defined `citationContract` with three citation-guidance keys. Producers have emitted five more since v3.0 and v3.2.1. All eight:

| Key | Type | Required | Meaning |
|---|---|---|---|
| `lastUpdated` | date | Yes | Date the citemap content was last generated. |
| `updateFrequency` | enum | No | How often the producer regenerates, using the v3.0 values: `daily`, `weekly`, `monthly`, `quarterly`, `annually`, `rarely`. Readers MAY use it to decide when to re-fetch. |
| `canonicalSource` | URL | No | Where the authoritative copy of this file lives, normally `{origin}/citemap.json`. A copy found elsewhere SHOULD be treated as a mirror of this URL. |
| `contactForCorrections` | string | No | Email address (or URL) for reporting a wrong fact. Producers SHOULD use an address someone at the entity reads; MUST NOT invent one. |
| `registryToken` | string | No | Registry claim token (v3.2.1, §10). |
| `disambiguation` | string | No | What the entity is NOT (v3.0). Mirrored as `brand.disambiguatingDescription` (§4.3). |
| `preferredName` | string | No | The exact name AI answers should use (v3.0). |
| `shortDescription` | string | No | One sentence AI answers may quote verbatim (v3.0). |

### 1.3 `citemap` (file authorship)

| Key | Type | Required | Meaning |
|---|---|---|---|
| `authorizedBy` | string | Yes | `"self"`: the entity authorized publication of this file (v3.0). |
| `contactForDisputes` | string | No | Who to contact if the file's authorization is disputed. |
| `generationId` | string | No | Producer's id for the generation that produced this file. Opaque to readers. |
| `generatedAt` | date-time | No | ISO 8601 timestamp of that generation. |

### 1.4 Dates are stable

`lastVerified`, `citationContract.lastUpdated`, `relationships[].observedAt` and `contentFiles[].lastUpdated` describe the record, not the request. Producers MUST NOT re-stamp them with the current time each time the file is served; they change when the record is regenerated. `observedAt` is stricter still (§3.5).

## 2. Foundational sections: updated definitions

The ten always-on sections of v3.3 §3 are unchanged in v3.5. This section gives full definitions to the ones v3.3 only sketched, and amends one rule for content files.

### 2.1 Always-on sections and content files

When a foundational array moves to content files (§8; in v3.5 this applies only to `brand.products`), the main file's `contentFiles[]` entry for that type satisfies the always-on rule. The main file MUST NOT also carry an empty `brand.products: []` in that case, because an empty array would read as "this entity has no products". Readers that need the section MUST follow the content file.

### 2.2 `trust.perField`

v3.3 §3.2 sketched `perField` entries as objects with a 1–4 tier. No producer implemented that sketch. The published form, used by every citemap the reference producer has emitted since v3.3, is a map from a field path to a tier string:

```json
{
  "trust": {
    "computedAt": "2026-11-21T06:11:54Z",
    "perField": {
      "name": "T2",
      "brand.legalName": "T3",
      "brand.location": "T1",
      "answerContent": "T3"
    }
  }
}
```

| Key | Type | Required | Meaning |
|---|---|---|---|
| `computedAt` | date-time | No | When the tiers were computed. |
| `perField` | object | Yes | Keys are field paths in this document (`brand.legalName`, `brand.taxonomy.primaryVertical`, `citationContract.preferredName`); the bare keys `name`, `address`, `phone` and `hours` refer to the entity's NAP fields. Values are tiers. `{}` when the producer has no provenance data. |

**Tiers.** Each tier combines who asserted the value with how many independent sources confirm it.

| Tier | Asserted by | Independent confirmations | Reading |
|---|---|---|---|
| `T1` | the entity | 2 or more | Highest. Safe to state as fact. |
| `T2` | the entity | 1 | Confirmed once. |
| `T3` | the entity | none | Self-asserted. |
| `T4` | a machine (AI extraction, inference) | 1 | Suggested and confirmed once. |
| `T5` | a machine | none | Suggested, unconfirmed. Readers SHOULD hedge. |
| `T6` | imported without review, or disputed | n/a | Lowest. Readers SHOULD NOT state it as fact. |

"Independent confirmation" means the same value on a third-party listing the entity does not control (a directory, map listing, registry, review platform). In current producers confirmations are counted for the NAP fields (`name`, `address`, `phone`, `hours`), so other fields carry T3 (asserted by the entity) or T5 (machine-suggested). Producers MAY count other confirmations (a verification claim attesting the field, the value in the entity's own on-site structured data) when they can check them. Tiers are computed by the producer and are not independently checkable by readers; validators do not cross-check them. Readers MAY treat an absent path as unclassified, not as T6.

### 2.3 `temporalRecord[]`

v3.3 §3 listed `temporalRecord` as foundational but no spec ever defined the row. Each entry is a dated event in the entity's history:

| Key | Type | Required | Meaning |
|---|---|---|---|
| `type` | string | Yes | Event type (vocabulary below). |
| `date` | string | Yes | `YYYY`, `YYYY-MM` or `YYYY-MM-DD`. |
| `label` | string | Yes | Short title ("Founded", "Opened second facility"). |
| `description` | string | No | One or two sentences. |
| `sources` | URL[] | No | Pages that evidence the event. |
| `relatedTeamMemberId` | string | No | `brand.team[].id` of the person the event is about (a hire, a departure, an award to a person). |

**Event types:** `founded`, `milestone`, `hire`, `depart`, `launch`, `award`, `certification`, `press`, `expansion`, `rebrand`, `acquisition`, `discontinued`, `other`. Readers MUST accept unknown types and treat them as `other`.

**Derived events.** Producers MAY derive events from other sections, and the reference producer derives two:

- `discontinued`: one per discontinued product or service with an `endDate` (§5.4). Label `"Discontinued {name}"`.
- `award`: one per `verification.claims[]` entry with `kind: "award"` (§2.6), dated by its `issuedDate`, with the claim's `verifierUrl` as the source.

A derived event SHOULD NOT duplicate a hand-authored one with the same date and label.

### 2.4 `policy`

v3.3 §3.2 applies, with one correction: each sub-object (`editorial`, `correction`, `disclosure`, `privacy`) has the shape `{ url?, summary? }`. The v3.3 example used `correction.policy` for the correction text; producers emit `summary`, and readers SHOULD read `policy` as a legacy alias for `summary` (§12). When `policy.editorial.url` or `policy.correction.url` is set, producers SHOULD mirror it on the brand as `publishingPrinciples` / `correctionsPolicy` (schema.org).

### 2.5 `answerContent[]`

Unchanged from v3.0: `{ question, answer }` entries. Entries SHOULD be answers a person at the entity approved for publication. A record with no approved answers MAY carry machine-drafted ones; its `trust.perField.answerContent` tier SHOULD then be `T5` (§2.2), so readers can tell drafted answers from approved ones.

### 2.6 `verification`

v3.3 §3.2 applies. Two additions:

| Key | Where | Type | Meaning |
|---|---|---|---|
| `kind` | `claims[]` | enum | `certification`, `license`, `accreditation`, `membership`, `award`, `other`. Optional; readers MUST treat an absent kind as `other`. |
| `lastUpdated` | `verification` | date | When the claims list last changed. |

Awards with a verifiable issuer are claims with `kind: "award"`; they are no longer published as `brand.publications[]` entries (§6.5). Memberships in a regulatory, government or certifying body belong here with `kind: "membership"` or `license`, not in `brand.memberOf` (§7.3).

### 2.7 `verifiedClaims[]`

v3.0 §5 defined registered identifiers as `{ type, identifier, entity?, registryUrl? }`, where `type` is one of the v3.0 claim types (NPI, EIN, state license and the rest). v3.5 makes the row shape validator-enforced (§13): `type` and `identifier` are required. Type values are matched case-insensitively against the v3.0 list; unknown types are a warning, not an error. An older, non-spec row shape (`claimType`, `issuer`, `verifiedDate`, with values such as `NPI` and `bar-number`) was emitted by early producers; it is deprecated (§12). Readers SHOULD read `claimType` as `type` and map `bar-number` to `bar-license`.

### 2.8 Vertical module keys

Per-vertical data (v3.0 "modules") stays optional and producer-defined; v3.5 still defines no per-vertical schemas (v3.3 §10.2). One naming rule: a module's top-level key SHOULD be the vertical's `primaryVertical` value from the registry (`healthcare`, `real-estate`, `legal-services`), or its v3.0 module key for verticals that existed in v3.0. Producers SHOULD NOT invent abbreviated keys (`local`, `realestate`, `research`); validators SHOULD warn on keys that are neither (§13). Module contents MAY use dotted keys (`"healthcare.insurance"`). Module keys MUST NOT reuse a foundational key (`trust`, `temporalRecord`, `policy`, `verification`, `answerContent`); a module named like a foundational section would overwrite it.

## 3. Graph vocabulary

v3.3 §1–§2 defined `@graph[]`, `relationships[]` and 13 edge types. v3.5 adds node types, 16 edge types, a recommended `@id` scheme and a clarified reachability rule. Everything in v3.3 §1–§2 not amended here stays in force.

### 3.1 New edge types

Producers have emitted these types since mid-2026, first as bare names and, since November 2026, under the extension namespace `https://citemaps.org/ext/v1/types/{name}` (the v3.3 §2.3 custom-type mechanism). v3.5 graduates them into the registry. Each has a registry URI at `https://citemaps.org/v3.5/types/{name}`.

**Schema.org-aligned types.** Named after a schema.org property; where the inline property is noted, producers SHOULD also set it on the node (v3.3 §1.6 mirroring).

| Type | From → to | Inline mirror | Meaning |
|---|---|---|---|
| `brand` | primary → Brand | `brand.subBrands[]` | The entity owns or sells this brand. Emitted for brands not tied to a location; brands made at a location connect through `producedAt` instead. |
| `manufacturer` | Product → primary | `Product.manufacturer` | The entity makes this product. |
| `makesOffer` | primary → Product | `Product.offers.offeredBy` | The entity sells a product it does not make (distributors, retailers, resellers). See §5.2. |
| `creator` | MediaChannel, VideoObject, publication or PodcastEpisode → Person | `creator` | The person who made the work. Distinct from appearing in it (`featuring`, or `actor` on a video). |
| `about` | VideoObject, publication, PodcastEpisode or Event → Brand, Product, Place or Organization | `about` | The work is about that brand, product, location or organization. |
| `recordedIn` | Event → VideoObject | `Event.recordedIn` | A recording of the talk. |

**Citemap-native types.** No schema.org equivalent; relationship row only.

| Type | From → to | Meaning |
|---|---|---|
| `authored` | primary → work | The entity produced the work (its own article, video, podcast episode, talk). |
| `featuredIn` | primary → work | The entity appears in someone else's work (a guest spot, an interview, a panel). |
| `mentionedIn` | primary → work | The entity is named in the work but is not its subject or a participant. |
| `publishedOn` | VideoObject or PodcastEpisode → MediaChannel | The channel or show the item was published on. |
| `channelOf` | MediaChannel → primary | The channel belongs to the entity. Omitted when the channel belongs to a team member (§6.2); the channel then reaches the entity through `creator` → Person → `worksFor`. |
| `producedAt` | Brand → Place | The brand is made at this location (§5.6). |
| `featuring` | publication, PodcastEpisode or Event → Person | A person who appears in the work (guest, speaker, interviewee). |
| `client` | primary → Organization | The organization is a client of the entity (§7.4). |
| `agency` | primary → Organization | The organization is an agency serving the entity (§7.4). |
| `partner` | primary → Organization | A named business partner (§7.4). |

"work" means a `@graph` node for a publication, video, podcast episode or talk (§3.3). `client` and `partner` reverse the v3.3 §2.4 rejections of `partnerOf` and `customerOf`, with the condition that answers the confidentiality concern v3.3 raised: an entry is published only when the entity chooses to publish it and a public page names both parties (§7.4).

### 3.2 Short names and extension URLs are the same type

For every type in §3.1, the short name and `https://citemaps.org/ext/v1/types/{name}` are the same type. Readers MUST treat them as equal. Validators MUST accept both and MUST NOT warn on either. Producers SHOULD emit the short name in v3.5 documents. The extension form never stops being valid, so documents published before v3.5 keep validating cleanly (v3.3 §2.6).

### 3.3 Node types

v3.3 nodes (`Person`, `Place`, `Organization` for parents, subsidiaries, memberships and storefronts) carry forward. v3.5 adds:

| Node | `@type` | Main properties (not exhaustive) | Defined in |
|---|---|---|---|
| Brand | `Brand` | `name`, `url`, `sameAs`, `subjectOf` | §5.6 |
| Product | `Product`, or `ProductGroup` when the product has variants | `name`, `url`, `sku`, `description`, `brand`, `manufacturer` or `offers.offeredBy`, `subjectOf` | §5.1–§5.3 |
| Channel | `["Organization", "https://citemaps.org/ext/v1/types/MediaChannel"]`, plus `"PodcastSeries"` for podcast shows | `name`, `url`, `image`, `sameAs` (other platforms), `creator`, `description` | §6.2 |
| Video | `VideoObject` | `name`, `url`, `contentUrl`, `embedUrl`, `thumbnailUrl`, `uploadDate`, `duration`, `publisher`, `actor`, `creator`, `about`, `publication` (BroadcastEvent for live) | §6.3 |
| Publication | `Article` (article, case study), `Report` (white paper), `NewsArticle` (press release), `SocialMediaPosting` (social post), `Review` (testimonial) | `name`, `headline`, `url`, `datePublished`, `publisher`, `author`, `creator`, `about`, `mentions` | §6.5 |
| Podcast episode | `PodcastEpisode` | `name`, `url`, `datePublished`, `timeRequired`, `episodeNumber`, `partOfSeason`, `partOfSeries`, `publisher`, `image`, `associatedMedia` (AudioObject), `video` (VideoObject), `actor`, `creator`, `about`, `mentions` | §6.4 |
| Talk | `Event` | `name`, `startDate`, `endDate`, `eventStatus`, `eventAttendanceMode`, `location`, `organizer`, `performer`, `superEvent`, `recordedIn` | §6.6 |
| Client, agency, partner | `Organization` | `name`, `url`, `sameAs`, `subjectOf` | §7.4 |

`MediaChannel` is a citemap type with no schema.org equivalent. In `@type` it is written as the absolute IRI `https://citemaps.org/ext/v1/types/MediaChannel`, because JSON-LD resolves bare terms through `@context` and the citemap `@context` value is an identifier, not a context document. Readers MUST NOT require a bare `MediaChannel`. The same applies to any future citemap node type.

**Existing v3.3 nodes, clarified.** `Place` nodes SHOULD carry `address` (a schema.org `PostalAddress`) and MAY carry `telephone` and `openingHoursSpecification` (§5.5). Membership organization nodes MAY carry `url` and `sameAs`.

**Free-text targets.** When a connection target is named but has no node (a guest who is not on the team, a brand the entity does not own), producers emit it inline (`{ "@type": "Person", "name": "…" }`) on the node and emit no relationship row.

**Non-schema.org properties on nodes.** Nodes MAY carry properties that schema.org does not define (`platform`, `customPlatform`, `subscriberCount`, `sessionType`). JSON-LD processors drop them; citemap readers MAY use them. Producers SHOULD put a fact in a schema.org property when one exists.

### 3.4 Recommended `@id` scheme

`@id` values are producer-chosen. The scheme below is RECOMMENDED so that ids are stable across regenerations and readable across files. `{id}` is the entry's `id` in the matching `brand.*` array; `{slug}` is a lowercase, hyphenated form of the name.

| Node | `@id` |
|---|---|
| Primary entity | `{origin}/#org` (for person entities too) |
| Team member | `{origin}/#person-{id}` |
| Location | `{origin}/#location-{id}` |
| Brand | `{origin}/#brand-{slug}` |
| Product | the product page's origin and path plus `#product` (query string dropped) when its `pageUrl` is on the entity's own host, the same id the product page's own schema.org markup uses; otherwise `{origin}/#product-{id}` |
| Storefront | `{origin}/#storefront-{id}` |
| Membership organization | `{origin}/#membership-{slug}` |
| Client, agency, partner | `{origin}/#client-{slug}`, `#agency-{slug}`, `#partner-{slug}` (with a short id suffix when two names give the same slug) |
| Other related organization | its own citemap `@id` when it publishes one; else `{origin}/#rel-{id}` |
| Channel | `{origin}/#channel-{id}` |
| Video | `{origin}/#video-{id}` |
| Publication | `{origin}/#publication-{id}` |
| Podcast episode | `{origin}/#podcast-{id}` |
| Talk | `{origin}/#speaking-{id}` |

An `@id` MUST identify the same thing in every file of a record (§8) and SHOULD stay the same across regenerations. `@id`s MUST be unique within the joined record.

### 3.5 Relationship rows

v3.3 §1.4 applies. Clarifications:

- **`observedAt`** is the date the edge first appeared in this entity's published citemap. Producers MUST keep it stable across regenerations (store the first-seen date per edge) and MUST NOT set it to the generation date on each run. A producer that has no first-seen history MAY use the generation date once; it then stays fixed. Hand-authored edges MAY carry the date the relationship began instead.
- **`context`** is free text that qualifies the edge: the membership level and start date on `memberOf` ("Member · Gold · member since 2019"), the services and dates on `client` ("Media Relations · since 2024-07"), the vertical on `operatesAs` (v3.3 §1.8).
- **`source`** is a URL evidencing the edge: the membership directory listing, the case study or press release naming the client.
- **`verified`** stays validator-computed (v3.3 §2.5). Producers SHOULD NOT emit it.
- Producers SHOULD NOT emit two rows with the same `from`, `type` and `to`.

### 3.6 Reachability

v3.3 §1.3 requires every `@graph` node to be reachable from the primary entity through `relationships[]`. v3.5 states how reachability is measured:

- **Edges count in either direction.** `worksFor` (Person → primary), `locationOf` (Place → primary), `manufacturer` (Product → primary) and `channelOf` (MediaChannel → primary) all point toward the primary entity; they connect their nodes all the same.
- **Paths may pass through other nodes.** A channel that belongs to a team member is reached by `creator` → Person → `worksFor` → primary, with no `channelOf` row. A brand made at a location is reached by `producedAt` → Place → `locationOf` → primary. A video on a channel is reached through `publishedOn` → channel.
- **Content files join first.** For a record split into content files (§8), reachability is measured on the joined record, not on each file alone.

A node with no path to the primary entity is an orphan and MUST fail validation (v3.3 §9.3, unchanged).

### 3.7 `subjectOf` on nodes and catalog entries

A third-party page about a specific product, person, location, brand, membership or client is attached to that node as `subjectOf`, not only to the brand. Catalog entries that have no `@graph` node (`brand.services[]`, `brand.productCategories[]`, `brand.serviceCategories[]`) carry `subjectOf` on the entry itself.

- Shape: the same CreativeWork form as `brand.subjectOf` (§7.2).
- **Exact tagging:** a page attaches to a node only when it names that node. It MUST NOT be inherited from a parent (a page about a product category does not attach to every product in it).
- Producers SHOULD cap `subjectOf` at 5 entries per node or entry, choosing the strongest pages, and MAY cap the total across the file.
- Per-node entries carry no `corroboratedBy` provenance (§7.1); the brand-level `corroboratedBy[]` is the inventory.

## 4. Brand and identity fields

### 4.1 `brand.@type`

The brand object's `@type` is the schema.org type that best fits the entity. Producers SHOULD use `Person` for a person entity, `Restaurant` for the restaurant vertical, `GovernmentOrganization` for government, `LocalBusiness` for an entity with a physical location serving local customers, and `Organization` otherwise. A more specific schema.org type MAY be used when the producer knows it.

### 4.2 New brand fields

| Key | Type | Meaning | schema.org |
|---|---|---|---|
| `alternateName` | string | Legal DBA or other trade name. | `alternateName` |
| `shortName` | string | How the entity refers to itself in short (an acronym such as "ABC"). | `areaServed` | string[] | The entity's service area (cities, regions, countries, "nationwide"). v3.3 defined `areaServed` only per service. | `areaServed` |
| `notableFor` | string or string[] | What the entity is known for. v3.0 defined a single sentence; a list of short items is now also valid. Readers MUST accept both. | n/a |
| `numberOfEmployees` | enum | `1-10`, `11-50`, `51-200`, `201-500`, `501-1000`, `1001-5000`, `5000+`. | `numberOfEmployees` |
| `mission` | string | Mission statement. | n/a |
| `languagesSupported` | string[] | Languages the entity serves customers in. | `knowsLanguage` |
| `guarantees` | string[] | Guarantees and warranties the entity offers ("Lifetime workmanship warranty"). | n/a |
| `accessibility` | string[] | Accessibility features ("Wheelchair accessible entrance"). | `amenityFeature` |
| `diversityOwnership` | string[] | Ownership certifications or self-identifications the entity chooses to publish ("Woman-owned"). Producers MUST publish only what the entity chose to state. | n/a |

| `expertise` | string[] | Areas of expertise (v2.0, still emitted). | `knowsAbout` |
| `audiencePrimary` | string | Primary audience (v2.0, still emitted). | `audience` |
| `publishingPrinciples` | URL | Mirror of `policy.editorial.url` (§2.4). | `publishingPrinciples` |
| `correctionsPolicy` | URL | Mirror of `policy.correction.url`. | `correctionsPolicy` |

`brand.founded` is a string (`YYYY` or `YYYY-MM-DD`). Readers SHOULD accept a number for documents from earlier producers.

### 4.3 What the entity is not: `disambiguatingDescription` and `distinctFrom[]`

v3.0 defined `citationContract.disambiguation`, a sentence saying what the entity is not. It is mirrored on the brand as `disambiguatingDescription` (schema.org), so readers that only parse the brand object see it.

`brand.distinctFrom[]` is the structured form: entities that are easily confused with this one and are not it.

| Key | Type | Required | Meaning |
|---|---|---|---|
| `name` | string | Yes | The other entity's name. |
| `url` | URL | No | Its website or profile. |
| `reason` | enum | No | `same-name-different-location`, `similar-name`, `former-affiliate`, `imposter`, `unrelated`. |
| `note` | string | No | One sentence of context. |

`distinctFrom` is an anti-coreference assertion: readers SHOULD NOT merge facts about a listed entity into this one. Two entities that list each other are a mutual assertion a validator MAY check across documents (v3.3 §1.7). The edge form of this list is deferred (§15).

### 4.4 Location headline: `brand.location`

`brand.location` (`{ city, state, country? }`, v3.0) is the entity's headline location. When `brand.locations[]` has a primary entry, `brand.location` SHOULD mirror it (`region` → `state`). Merging the two into one source is a breaking change and is deferred to a major version.

### 4.5 Taxonomy version

`brand.taxonomy.taxonomyVersion` SHOULD name the registry release the producer authored against. The v3.5 registry is `2026-11` (§14).

### 4.6 Team: former members and personal contact details

v3.3 §4.5 applies. Two rules restated because producers have broken or changed them:

- **Former members** (`formerlySince` set) stay in `brand.team[]` with their dates and MUST NOT appear in `brand.employee[]` (v3.3 §4.5, unchanged). Their Person node MAY keep its `worksFor` edge with an `observedAt` from their tenure (v3.3 §4.5), which also keeps nodes that point at them (a channel they created, a talk they gave) reachable.
- **Personal contact details.** Producers SHOULD NOT publish team members' personal email addresses or phone numbers. The company's public email and phone are the contact points. The fields stay valid for entities that deliberately publish them.

## 5. Catalog and locations

### 5.1 `brand.products[]` additions

v3.3 §4.7 applies. Added fields:

| Key | Type | Meaning |
|---|---|---|
| `variesBy` | string[] | Attributes the product's variants differ on (`"color"`, `"size"`, `"thickness"`). Present only on products with variants. |
| `variants[]` | object[] | One entry per variant: `attributes` (object, the varying values, required), `sku`, `gtin`, `availability`, `imageUrl`, `priceRange`. |
| `lifecycle` | object | Discontinuation (§5.4). |

`specifications` MAY be a string or an object; readers MUST accept both. Third-party pages about a product are `subjectOf` on its graph node (§3.7), not on the entry. `productType` SHOULD be set; when the producer has no explicit type it MAY use the product's first category name.

### 5.2 Product nodes and the reseller pattern

Each catalog product SHOULD have a sparse `@graph` node (`@type: Product`, or `ProductGroup` when it has `variesBy`), so other nodes can point at it (`about`, `subjectOf`). The full variant tree stays inline in `brand.products[]`; a `ProductGroup` node MAY omit `hasVariant` and `variesBy`.

The node's `@id` follows §3.4: when the product has its own page on the entity's site, the id is that page's URL plus `#product`, so the citemap node and the product page's own schema.org markup are the same node.

How a product connects to the entity depends on whether the entity makes it. Producers MAY decide this per entity (the reference producer treats distribution, retail and ecommerce entities without the `manufacturing-direct` modifier as resellers) or per product:

- **The entity makes it:** a `manufacturer` edge (Product → primary) and inline `Product.manufacturer: { "@id": primary }`.
- **The entity sells it but does not make it** (distributors, wholesalers, retailers, resellers): a `makesOffer` edge (primary → Product) and inline `Product.offers: { "@type": "Offer", "offeredBy": { "@id": primary } }`. Producers MUST NOT claim `manufacturer` for products the entity does not make.

`Product.brand` SHOULD point at the catalog Brand node (`{ "@id": … }`) when the product's brand matches one of `brand.subBrands[]`; otherwise it is an inline `{ "@type": "Brand", "name": … }`.

### 5.3 Brand nodes

Every `brand.subBrands[]` entry SHOULD carry its catalog `id` and SHOULD have a `Brand` node (`#brand-{slug}`). A brand made at a location reaches the entity through `producedAt` (§5.6); every other brand gets a `brand` edge (primary → Brand).

### 5.4 Discontinued offerings: `lifecycle`

Removing a retired product or service from the citemap does not remove it from AI answers; the old fact lives on in other sources. Stating that it ended does more. Catalog entries (`brand.products[]`, `brand.services[]`) MAY carry:

| Key | Type | Required | Meaning |
|---|---|---|---|
| `lifecycle.status` | enum | Yes | `discontinued`. (`offered` is the default and is not emitted.) |
| `lifecycle.endDate` | date | No | When the entity stopped offering it. SHOULD be set. |

Rules:

- A discontinued entry SHOULD stay in the catalog with its `lifecycle` for 12 months after `endDate`. After that the producer MAY drop it; the `discontinued` event in `temporalRecord` (§2.3) keeps the dated record.
- Producers SHOULD emit a `discontinued` `temporalRecord` event for each discontinued entry with an `endDate`.
- Readers and registries MUST NOT present a discontinued entry as a current offering. A reader answering "does the entity offer X" SHOULD answer that it did until `endDate`.

### 5.5 `brand.locations[]` additions

v3.3 §4.8 applies. `id` stays REQUIRED on each entry (it anchors the `#location-{id}` node and the `locationOf` edge). Added fields:

| Key | Type | Meaning |
|---|---|---|
| `latitude` | number | WGS 84 latitude. |
| `longitude` | number | WGS 84 longitude. |
| `timeZone` | string | IANA time zone of the location (`America/Los_Angeles`). This is the location's zone, not the reader's. |
| `openingHours` | string[] | schema.org `openingHours` form: `"Mo-Fr 09:00-17:00"`, `"Sa 10:00-14:00"`. |
| `brands` | string[] | Names of the entity's brands made or produced here (§5.6). |

`country` SHOULD be an ISO 3166-1 alpha-2 code (`US`, `CA`). `hours` stays the human-authored free text. When the whole of `hours` can be read as schema.org day and time ranges, producers SHOULD also emit `openingHours` on the entry and `openingHoursSpecification[]` on the Place node; when any part of it cannot be read, producers MUST emit neither, rather than publish partial hours.

Third-party pages about a location are `subjectOf` on its Place node (§3.7).

### 5.6 Location → brand: `brands[]` and `producedAt`

For entities with several brands and several facilities (a brewery whose sites each make different labels), `brand.locations[].brands[]` lists the brands made at a location. Each value SHOULD exactly match a `brand.subBrands[].name`; validators SHOULD warn on names with no match. Producers MUST omit `brands` when empty. Each listed brand gets a `producedAt` edge from its Brand node to the location's Place node.

### 5.7 Categories and services

v3.3 §4.10 and §4.11 apply, including the 3-level nesting cap and cycle-breaking on category trees. Category entries and service entries MAY carry `subjectOf` (§3.7). Services MAY carry `lifecycle` (§5.4).

## 6. Media

Media is the entity's appearances and output: channels, videos, podcast episodes, talks, articles, press releases and social posts. v3.3 had one list (`brand.publications[]`) for all of it. v3.5 gives each format its own array, a shared set of fields, and a graph form, because each format has different facts AI answers use (an episode number, a talk's date and organizer, a video's watch page).

### 6.1 Shared fields

Every entry in `brand.video[]`, `brand.podcasts[]`, `brand.speaking[]` and `brand.publications[]` MAY carry:

| Key | Type | Meaning |
|---|---|---|
| `id` | string | Stable id; anchors the node `@id` (§3.4). SHOULD be set. |
| `role` | enum | `authored` (the entity's own work), `featured` (the entity appears in someone else's), `mentioned` (the entity is named in it). Required on videos; defaults to `authored` on publications and `featured` on podcasts and talks. |
| `platform` | string | Where it is hosted ("YouTube", "Spotify", "LinkedIn"). Free text. Distinct from `publisher`, who published it. |
| `image` | URL | Artwork or thumbnail. |
| `transcriptUrl` | URL | A transcript page or file. |
| `description` | string | Summary. |
| `connections[]` | object[] | Who and what the item involves (below). |

**Role on the graph.** The role emits an `authored`, `featuredIn` or `mentionedIn` edge from the primary entity to the item's node, and an inline mirror on the node: `featured` items get `about: { "@id": primary }`, `mentioned` items get `mentions: { "@id": primary }`, authored publications get `author: { "@id": primary }`, and an authored talk with no named organizer gets `organizer: { "@id": primary }`.

**Connections.** Each entry is `{ edge, targetType, targetId?, targetName? }`:

| `edge` | `targetType` | Emits |
|---|---|---|
| `about` | `brand`, `product`, `location`, `membership`, `relationship` | `about` on the node + an `about` edge |
| `about` | `org`, `service`, `category` | `about` on the node only (services and categories have no graph node) |
| `creator` | `person` | `creator` on the node + a `creator` edge |
| `featuring` | `person` | a `featuring` edge, plus the person on the node: `actor` on episodes and videos, `performer` on talks, `about` on publications |
| `publishedOn` | `channel` | a `publishedOn` edge + `publisher` / `partOfSeries` on the node |
| `recordedIn` | `video` | `recordedIn` on a talk + a `recordedIn` edge |

`targetId` is the id of the target's catalog entry (a `brand.team[].id`, a product id). `targetName` is for a target with no catalog entry; it emits an inline named object and no edge. Producers MUST drop connections whose target is not published in the same record.

### 6.2 `brand.channels[]`

A channel is a place the entity publishes a series: a YouTube channel, a podcast show, a LinkedIn newsletter.

| Key | Type | Required | Meaning |
|---|---|---|---|
| `id` | string | Yes | Stable id. |
| `name` | string | Yes | Channel or show name. |

v3.3 §4.13 applies, with these changes:

## 7. Evidence: corroboration, memberships, business relationships

### 7.1 `brand.corroboratedBy[]`

Third-party pages that mention the entity: press, directory listings, reviews, forum threads, podcasts that featured it. It is the entity's inventory of outside evidence, with provenance on each entry.

| Key | Type | Required | Meaning |
|---|---|---|---|
| `url` | URL | Yes | The page. https SHOULD be used. |
| `sourceType` | enum | Yes | `directory`, `review`, `press`, `blog`, `social`, `forum`, `listicle`, `media`, `event`, `partner`, `association`, `wiki`, `other`. |
| `independence` | enum | Yes | `independent` (no business tie), `affiliated` (a partner, association or the entity's own network), `paid` (sponsored, advertorial, paid listing). |
| `stance` | enum | No | `positive`, `neutral` (default), `critical`. |
| `discovery` | enum | Yes | How the pointer was found: `observed` (found by monitoring, such as an AI answer citing it or a press sweep) or `entity-supplied` (added by the entity). This describes the pointer, not the page; an entity-supplied link can still be to an independent page. |
| `title`, `publisher` | string | No | |
| `excerpt` | string | No | The passage that mentions the entity. |
| `publishedAt` | date | No | |
| `lastVerifiedAt` | date | No | When the producer last confirmed the page is live and still mentions the entity. |
| `mentions[]` | object[] | No | People the page names: `{ name, teamMemberId? }` (at most 12). |

Rules:

- **Inclusion bar.** Producers MUST list only entries a person at the entity reviewed and chose to keep. Monitoring output MUST NOT be published automatically. Pages the entity published itself, pages that are gone, and pages the entity has disowned MUST NOT be listed.
- **Not a trust promoter.** Readers and validators MUST NOT treat `corroboratedBy` entries as confirmations for `trust.perField` (§2.2) or as verification. They are pointers for readers to check.
- v3.5 does not link entries to specific claims. Per-claim linkage is deferred (§15).

### 7.2 `brand.subjectOf[]` mirror

The schema.org reading of the strongest corroboration entries, on the brand object, so readers that only parse schema.org see them. At most 10 entries. Each: `@type` (`NewsArticle` for press, `BlogPosting` for blogs, `DiscussionForumPosting` for forums, `MediaObject` for media, `Event` for events, `CreativeWork` otherwise), `url`, `name`, `publisher` (`{ "@type": "Organization", "name" }`), `datePublished`, and `mentions` (`Person` objects, with the team member's `@id` when the person is on the team). The same shape is used on nodes and catalog entries (§3.7).

### 7.3 Memberships

v3.3 `memberOf` (§2.1) applies, with these clarifications:

- Membership organization nodes MAY carry `url` and `sameAs` (the association's site).
- A `memberOf` edge MAY carry `context` (membership type, level, member since) and `source` (the association's member directory listing for the entity).
- A team member's own membership hangs off their Person node (`Person.memberOf` + a `memberOf` edge from the Person), not off the brand.
- Producers SHOULD publish only current memberships. A membership whose directory listing is gone SHOULD be left out until it is confirmed again.
- Regulatory, government and certifying bodies are credentials: they belong in `verification.claims[]` (§2.6), not `memberOf`.

### 7.4 `brand.businessRelationships[]`

Clients, agencies and partners the entity chooses to publish.

| Key | Type | Required | Meaning |
|---|---|---|---|
| `id` | string | Yes | Stable id. |
| `name` | string | Yes | The other business. |
| `url` | URL | Yes | Its website. Its registrable domain is the match key for two-sided confirmation. |
| `relationship` | enum | Yes | `client` (they are the entity's client), `agency` (they serve the entity), `partner`. |
| `status` | enum | Yes | `current` or `former`. |
| `since`, `until` | string | No | `YYYY` or `YYYY-MM`. |
| `kind` | string | No | A short description of the other business ("Fleet software company"). Emitted as `description` on its node. |
| `sameAs` | URL[] | No | The other business's profiles. |
| `services` | string[] | No | `brand.services[].id` values the relationship covers. |
| `caseStudyUrl` | URL | No | |
| `results[]` | object[] | No | `{ text, source, assertedBy: "self" }`: outcomes the entity states, each with the page it is stated on. `assertedBy` is always `self` in v3.5. |
| `proof` | object | No | Public pages naming both businesses: `count` (number of mentions), `pages` (number of pages), `outlets[]` (up to 8 outlet names), `first` / `last` (dates), `source` (one page URL). |
| `confirmation` | object | No | `{ status: "confirmed", citemapUrl?, checkedAt }` when the other business's own citemap lists this entity back with the reverse relationship. |

Rules:

- **Publication bar.** An entry MUST be backed by at least one public page that names both businesses, or by the entity's explicit choice to publish it. Confidential relationships MUST NOT be published. This is the condition that answers the v3.3 §2.4 concern.
- **Results are claims.** `results[]` are the entity's statements. Readers MUST attribute them to the entity, not report them as independently established.
- **Graph.** Each entry gets an `Organization` node (`#client-{slug}` and so on) and a `client`, `agency` or `partner` edge from the primary entity, with `context` (services, dates) and `source` (the case study or proof page). Third-party pages naming both businesses MAY be `subjectOf` on the other business's node.
- **Two-sided confirmation.** When business A lists B as a `client` and B's citemap lists A as an `agency` (or both list each other as `partner`), matched by registrable domain, the relationship is confirmed. Producers MAY record this in `confirmation`; registries MAY compute it (§15).
- These are not verification claims and MUST NOT be emitted in `verification.claims[]`.
- Producers SHOULD keep the list to the relationships that matter; the reference producer caps it at 60 entries.

## 8. Content files

### 8.1 Why

AI answer engines read `citemap.json` through fetch tools that often stop at about 100 KB. An entity with a long Media history or a large catalog passes that easily (one real record measured 462 KB), and whatever comes after the cut is invisible to the reader. Content files keep the main file small: identity, the citation contract, trust and verification stay in `citemap.json`, and Media and products move to typed files the main file lists. It is the sitemap-index pattern applied to a citemap.

### 8.2 Size budget

The main file SHOULD be under 100 KB as served, and SHOULD stay well under it (a target of 60 KB leaves room to grow). Each content file SHOULD also be under 100 KB. A record that fits in one file under the budget SHOULD stay one file; content files are for records that don't fit.

### 8.3 `contentFiles[]` in the main file

| Key | Type | Required | Meaning |
|---|---|---|---|
| `type` | enum | Yes | `publication`, `social-post`, `video`, `podcast`, `speaking`, `product`. |
| `url` | URL | Yes | Absolute https URL of the content file. MAY be on a different host from the main file. |
| `count` | integer | Yes | Number of items (rows) in the file. |
| `year` | string | No | When a Media type is split by year: `YYYY` or `undated`. |
| `category` | string | No | When products are split by category: the category name. |
| `part` | integer | No | When one year or category is still over budget and is split further: 1, 2, 3… in order. |
| `lastUpdated` | date | No | When the file's content last changed. |

`contentFiles` SHOULD come right after `brand`, so a reader that stops early still sees the index.

### 8.4 What moves and what stays

| Content type | Moves from | Stays in the main file |
|---|---|---|
| `publication` | `brand.publications[]` (except social posts) | |
| `social-post` | `brand.publications[]` with `contentType: "social-post"` | |
| `video` | `brand.video[]` | `brand.channels[]` |
| `podcast` | `brand.podcasts[]` | `brand.channels[]` |
| `speaking` | `brand.speaking[]` | |
| `product` | `brand.products[]` | `brand.productCategories[]`, `brand.subBrands[]` |

The items' `@graph` nodes and the relationship rows that belong to them move with them. A relationship row goes with its `from` node when that node is content; otherwise with its `to` node. Everything else stays in the main file.

A type moved to content files MUST be moved in full: items MUST NOT appear both inline and in a content file, and the main file MUST NOT keep the emptied array (§2.1). A producer MAY move some types and keep others inline.

### 8.5 The content file

```json
{
  "@context": "https://citemaps.org/v3.5",
  "@type": "CitemapContentFile",
  "version": "3.5",
  "contentType": "podcast",
  "year": "2023",
  "isPartOf": "https://example.com/citemap.json",
  "about": "https://example.com/#org",
  "count": 3,
  "lastUpdated": "2026-11-23",
  "brand": {
    "@id": "https://example.com/#org",
    "name": "Example Co.",
    "podcasts": [ { "id": "ep_1", "title": "…", "url": "https://…" } ]
  },
  "@graph": [ { "@type": "PodcastEpisode", "@id": "https://example.com/#podcast-ep_1" } ],
  "relationships": [ { "from": "https://example.com/#org", "to": "https://example.com/#podcast-ep_1", "type": "featuredIn", "observedAt": "2026-03-02" } ]
}
```

| Key | Type | Required | Meaning |
|---|---|---|---|
| `@context` | string | Yes | Same as the main file. |
| `@type` | string | Yes | `"CitemapContentFile"`. |
| `version` | string | Yes | Same as the main file. Files from earlier producers carry only `citemapVersion`; readers MUST accept either. |
| `contentType` | enum | Yes | One of the §8.3 types. MUST match the main file's entry. |
| `year`, `category`, `part` | | No | As in the main file's entry. |
| `isPartOf` | URL | Yes | The main file. SHOULD be its `citationContract.canonicalSource` or the URL the producer serves it from. |
| `about` | string | Yes | The primary entity's `@id`. MUST equal the main file's `brand.@id`. |
| `count` | integer | Yes | MUST equal the number of rows in `brand.<key>` and the main file's `count`. |
| `lastUpdated` | date | No | |
| `brand` | object | Yes | `@id`, `name`, and the one array for this type: `publications` (for `publication` and `social-post`), `video`, `podcasts`, `speaking` or `products`. |
| `@graph`, `relationships` | array | No | The items' nodes and edges, same `@id` scheme as the main file. |

### 8.6 Splitting a type

A type's file MAY split further when it is over budget:

- **Media** by year (from `publishedAt`, `uploadDate`, `datePublished`, `date` or `startDate`), newest first, `undated` last.
- **Products** by the first category's name (else `productType`, else "Uncategorized"), alphabetically.
- **Still too large:** a year or category over budget splits into numbered parts (`part`: 1, 2, …).

When a type splits, all of its items split by the same key. Nodes and edges that belong to no single item go in the first file of the type. Nothing is dropped for age or size; every item has a place in its type's files. File names are producer-chosen; `{type}-{year|category}[-{part}].json` is RECOMMENDED.

### 8.7 Reading

1. Read the main file. It is a valid citemap on its own.
2. For each `contentFiles[]` entry the reader needs, fetch `url`. Readers MUST accept only files the main file lists, and MUST discard a file whose `about` differs from the main file's `brand.@id` or whose `contentType` or `count` differs from the entry.
3. Append each file's `brand.<key>` rows, `@graph` nodes and `relationships` to the main file, skipping rows whose `id`, nodes whose `@id`, and edges whose `from`/`type`/`to` are already present.

The result is the one-file record. All rules in this spec (reachability, `@id` uniqueness, levels) apply to the joined record. A reader that cannot fetch a content file still has a valid main file, and SHOULD say it did not read the rest.

Trust flows from the main file: a content file on another host is part of the record because the main file lists it, not because of where it is hosted.

### 8.8 Serving

Content files SHOULD be served as `application/json` with permissive CORS (`Access-Control-Allow-Origin: *`) and the same caching as the main file. A producer MAY offer both forms (one file, or main file plus content files); sites whose own pages render from a single file often keep everything inline.

## 9. Citemap level

### 9.1 Why it changed

v3.0 §2 defined Level 2 as "at least one module" plus `answerContent` and `citationContract`. v3.3 replaced the module catalog with verticals and foundational sections (v3.3 §5), so the v3.0 test no longer measures anything meaningful: it depends on optional per-vertical keys whose names changed. Producers and validators implemented it differently and disagreed on the same file. v3.5 redefines the levels on foundational data only, so any reader computes the same level from the file alone.

### 9.2 Levels

| Level | Requirements | What it tells a reader |
|---|---|---|
| **1** | `brand.name`; `brand.url`; a description (`brand.aiSummary` or `citationContract.shortDescription`); a contact point (`brand.email`, a `brand.locations[].phone`, or `citationContract.contactForCorrections`); `lastVerified`. | Basic identity. |
| **2** | Level 1, plus at least one `answerContent` entry, plus `citationContract.preferredName` or `citationContract.shortDescription`. | Citation-ready: the entity says how to name and describe it and answers questions in its own words. |
| **3** | Level 2, plus at least one `verifiedClaims[]` entry with `type` and `identifier`. | Checkable identity: a registered identifier (license, NPI, EIN, registry number) a reader can look up. |

A document that does not meet Level 1 has no level; validators report what is missing. The level is computed on the joined record (§8.7).

### 9.3 `citemapLevel`

`citemapLevel` (1, 2 or 3) is the level the producer claims. Producers SHOULD compute it with §9.2. Validators compute the level themselves and SHOULD warn when the claim differs; a claim above the computed level is an inflation warning, a claim below it is informational.

DNS-verified ownership (§10.1) is a registry status, not a level: it depends on DNS, which a reader of the file alone cannot see.

## 10. Registry conventions

These describe how the citemaps.org registry treats published citemaps. They add no fields to citemap.json.

### 10.1 Claimed and Verified

- **Claimed:** the registry entry was claimed with the citemap's `citationContract.registryToken` (v3.2.1).
- **Verified:** the live citemap carries the `registryToken`, **and** a DNS TXT record at `_citemap.{registrable domain}` carries the same token. The registrable domain is found with the Public Suffix List; a site on a shared platform subdomain can be Claimed but not Verified.

Verified attests control of the domain, not identity. It is a live status: the registry re-checks it, and when the token or the TXT record disappears the entry returns to Claimed. Producers MUST keep `registryToken` stable and rotate it only when the entity asks.

### 10.2 Publisher-submitted citemaps

When the registry cannot fetch a site (a host firewall blocks it), an authenticated producer MAY submit the citemap's content with the registration. The registry lists a submitted copy only when its `registryToken` matches the `_citemap` TXT record, and labels it as submitted by the publisher's tool rather than fetched. How producers other than the reference producer obtain submission credentials is not yet specified (§15).

---

## 11. Producer guidance

- **Keep the main file small.** Use content files (§8) before cutting content. Social-post descriptions SHOULD be excerpts.
- **Publish what a person approved.** Q&A (§2.5), corroboration (§7.1) and business relationships (§7.4) are statements the entity makes about itself and others; producers MUST publish only entries a person at the entity approved.
- **Keep dates and ids stable** (§1.4, §3.4, §3.5). A citemap that changes every id and date on each run looks like a new record each time.
- **Don't publish personal contact details** of team members (§4.6).
- **Prefer schema.org.** Where a schema.org property exists, put the fact there; citemap-only properties are for facts schema.org has no place for.
- **Say what ended.** Mark discontinued offerings (§5.4) rather than deleting them.

## 12. Deprecations

### 12.1 Aliases (no warning)

Two forms are equal to their v3.5 counterparts and stay valid permanently. Validators MUST NOT warn on them.

- The extension-URL form of each §3.1 edge type (`https://citemaps.org/ext/v1/types/{name}`). Producers SHOULD emit the short name.
- `citemapVersion`, equal to `version`. Producers MAY emit both while readers written against v3.0 exist.

### 12.2 Deprecated forms

Deprecated forms stay valid. Validators SHOULD warn and MUST NOT fail. Readers SHOULD keep reading them. None are removed before a major version.

| Deprecated | Use instead | Since |
|---|---|---|
| `primaryVertical` / `additionalVerticals` aliases `legal`, `financial`, `events`, `research` | `legal-services`, `financial-services`, `events-venue`, `science-research` | v3.3 renames. v3.4 announced that v3.5 would drop them; v3.5 deprecates them instead, so earlier files keep validating. Producers MUST stop emitting them. |
| `brand.video[].contentUrl` holding the watch page | `url` for the page; `contentUrl` only for a media file | v3.5 |
| `verifiedClaims[]` rows with `claimType` / `issuer` / `verifiedDate` | `{ type, identifier, entity?, registryUrl? }` (v3.0 §5) | v3.5 |
| `publications[].contentType` `podcast`, `video`, `testimonial`, `award` for new entries | `brand.podcasts[]`, `brand.video[]`, `corroboratedBy[]`, `verification.claims[]` with `kind: "award"` | v3.5 |
| `policy.correction.policy` | `policy.correction.summary` | v3.5 |
| Abbreviated vertical module keys (`local`, `realestate`, `research`) | the vertical value or v3.0 module key (§2.8) | v3.5 |
| `trust.perField` object entries (`{ tier, sources, lastVerifiedAt }`, the v3.3 sketch) | tier strings `T1`–`T6` (§2.2) | v3.5 |

The four retired `primaryVertical` values of v3.3 §6 (`local-business`, `manufacturer`, `membership-org`, `industrial-services`) keep their v3.3 status: valid, not recommended, with a migration warning.

## 13. Validator behavior

v3.3 §9 applies. Changes and additions for v3.5:

**MUST (errors)**

- §13.1 Accept every §3.1 type in both its short and extension-URL forms.
- §13.2 Measure reachability per §3.6 (either direction, through other nodes, on the joined record). Orphans fail.
- §13.3 `@id` unique across the joined record, including across content files.
- §13.4 Content files: `@type`, `contentType`, `about` and `count` consistent with the main file's entry (§8.5); items not both inline and in a content file (§8.4).
- §13.5 `verifiedClaims[]` rows have `type` and `identifier`. Legacy rows (§12) are read as `type` = `claimType` and warned, not failed. `type` values are matched case-insensitively against the v3.0 list; an unknown type is a warning.
- §13.6 Required fields of the entries defined in §4–§8 are present (for example `corroboratedBy[].url` / `sourceType` / `independence` / `discovery`, `businessRelationships[].url` / `relationship` / `status`, `channels[].platform`, `contentFiles[].type` / `url` / `count`), and enumerated fields new in v3.5 (`businessRelationships[].relationship`, `corroboratedBy[].sourceType` / `independence` / `discovery`, `lifecycle.status`, `channels[].platform`, `numberOfEmployees`) carry a listed value.
- §13.7 A vertical module key that reuses a foundational key (§2.8).

**SHOULD (warnings)**

- §13.8 Compute the citemap level (§9.2); warn when `citemapLevel` differs, and say which requirement is missing for the next level.
- §13.9 Deprecated forms (§12).
- §13.10 Main file or a content file over 100 KB (§8.2).
- §13.11 `locations[].brands[]` names with no matching `subBrands[].name` (§5.6).
- §13.12 `openingHours` values that don't match the schema.org form: day codes (`Mo`…`Su`) as a range (`Mo-Fr`) or a comma list (`Mo,We,Fr`), a space, then `HH:MM-HH:MM` (§5.5).
- §13.13 `lifecycle.status: "discontinued"` without `endDate` (§5.4).
- §13.14 `answerContent` entries whose `trust.perField` tier is `T5` or `T6` are reported, so producers see drafted answers (§2.5).
- §13.15 Validator output MUST NOT count `corroboratedBy[]` entries as trust or verification (§7.1).
- §13.16 Vertical module keys that are neither a registry vertical nor a v3.0 module key (§2.8).
- §13.17 `relationships[].observedAt` that is not a date, or rows duplicated by `from`/`type`/`to` (§3.5).
- §13.18 `businessRelationships[].results[]` entries without `source` (§7.4).

**MAY (advisory)**

- §13.19 Check `distinctFrom` and `businessRelationships` mutually across documents (§4.3, §7.4) and report matches as informational.
- §13.20 Fetch content files and report which were not read.

## 14. Migration v3.4 → v3.5

**Minimum change:** set `version` (and `citemapVersion`, if emitted) to `"3.5"` and `@context` to `"https://citemaps.org/v3.5"`. Every v3.4 document is then a valid v3.5 document.

**Full v3.5 emission:**

1. Emit short names for the §3.1 edge types.
2. Set `brand.taxonomy.taxonomyVersion` to `"2026-11"` and stop dual-writing the v3.3 vertical aliases.
3. Compute `citemapLevel` with §9.2.
4. Keep `observedAt` first-seen dates stable (§3.5).
5. Remove former team members from `employee` (§4.6).
6. Name vertical module keys per §2.8.
7. Add `version` to content files (§8.5) and drop the emptied `brand.products` from a split main file (§2.1).
8. Mark machine-drafted `answerContent` as `T5` (§2.5), and keep `channelOf` on channels whose creator is not a team member (§6.2).

**For readers:** accept both edge-type forms; treat `MediaChannel` as an IRI; follow `contentFiles` when you need Media or products; read `notableFor` as a string or a list; read `trust.perField` tier strings.

**Registry vocabulary:** [v3.5-vocabulary.md](./registry/v3.5-vocabulary.md), registry version `2026-11`, adds the 16 edge types, the node types, and the enumerations defined here.

## 15. Not in v3.5

Proposed, but not emitted by any producer yet, so left for a later version:

- **Agent interface layer:** `agentCapabilities[]`, `agentPolicy`, `/.well-known/citemap-binding.json`.
- **Dynamic-data modules:** facet summaries with a pointer to a live query, for inventory, listings and rates.
- **Edge confidence** (`declared` / `inferred`), **`canonicalLabel`**, and an **evidence publisher exact-match** rule.
- **Custom node types** through `additionalType` (the node-side twin of v3.3 §2.3).
- **Product spec profiles:** `products[].specs` with a `specSet`.
- **`coreferentActor`** identity edges and the edge form of `distinctFrom`.
- **Video trust ladder** and trust by transitivity for `authored` media.
- **Registry pair-matching** for business relationships and signed attestation of `discovery: observed` corroboration.
- **Per-claim corroboration** linking `corroboratedBy` entries to specific facts.
- **A typed `brand.memberships[]`** (type, level, since, status, directory URL) and `ProgramMembership` nodes.
- **One location source:** merging `brand.location` into the primary `brand.locations[]` entry (breaking; major version).
- **Producer credentials** for publisher-submitted citemaps.
- **A markdown companion** (`citemap.md`) and `llms.txt` pointers.
